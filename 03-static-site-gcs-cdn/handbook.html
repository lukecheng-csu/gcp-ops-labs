整体架构

用 4 个 GCP 服务拼一个「https 可访问、图片走 CDN 缓存」的静态站：

用户浏览器
→

→

→
Cloud Storageindex.html / img/test.jpg
↳

服务今天的角色成本

前置条件

今天在腾讯云跳板机（Rocky Linux）上装好了 gcloud，这三件事必须都过：

# 1) gcloud 能跑（PATH 已配好，见坑 1）
gcloud --version

# 2) 已登录（跳板机无浏览器，必须用 --no-browser）
gcloud auth login --no-browser

# 3) 项目已锁定
gcloud config set project lukechengtest
gcloud config list --format='value(core.project)'   # lukechengtest
关键变量（后面命令都会用到）：项目 lukechengtest、bucket lukecheng-static-site、域名 static.cloudworkflowdone.com、LB IP 136.82.37.171。

第一步：建 bucket + 上传内容

1.1 建 bucket

全局唯一名；us-central1 吃免费额度；uniform 统一权限模型。

gcloud storage buckets create gs://lukecheng-static-site \
  --location=us-central1 \
  --uniform-bucket-level-access

1.2 准备本地静态内容

目录结构要和 index.html 里的引用路径严格一致，否则页面破图。

mkdir -p ~/static-site/img
cd ~/static-site

写 index.html（注意 src="/img/test.jpg" 要和后面上传的路径一字不差）：

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Static Site on GCP</title>
</head>
<body>
  <h1>Hello from Cloud Storage + Cloud CDN</h1>
  <p>Served from a Cloud Storage bucket through an HTTPS Load Balancer.</p>
  <img src="/img/test.jpg" width="320" alt="test image">
</body>
</html>

放一张测试图到 img/test.jpg（内容无所谓，就是给 CDN 缓存验证用的）。

1.3 上传并验证

gcloud storage cp -r . gs://lukecheng-static-site/

gcloud storage ls -r gs://lukecheng-static-site/

预期输出（只有这两个文件就对了）：

gs://lukecheng-static-site/index.html
gs://lukecheng-static-site/img/test.jpg
坑：macOS 的 .DS_Store 会被一起传上去
cp -r . 会把 Finder 自动生成的隐藏文件也带上。删掉它，或上传时排除： 
gcloud storage rm gs://lukecheng-static-site/.DS_Store
# 或者上传时就排除
gcloud storage cp -r . gs://lukecheng-static-site/ --exclude='.DS_Store'

第二步：建 LB 骨架 + HTTP 前台

为什么先只做 HTTP(80)，不做 HTTPS？
HTTPS 需要证书，而 Google 托管证书必须靠 DNS 验证；DNS 委派是第三步。现在硬建 443，证书会一直卡在 PROVISIONING，看起来像坏了。
所以顺序是：先建 80 把 LB → bucket 链路跑通，等 DNS 通了再补 443 + 证书。每步都有可验证的结果。

五条命令，一条一个组件，顺序不能乱（后面的引用前面的）：

2.1 预留全局静态 IP

LB 的固定入口，第三步 DNS 要指向它。

PROJECT=lukechengtest

gcloud compute addresses create static-site-ip --global --project=$PROJECT

# 记下这个 IP
gcloud compute addresses describe static-site-ip --global \
  --project=$PROJECT --format='value(address)'
# 136.82.37.171

2.2 建 backend bucket（把 GCS 挂成 LB 后端）

这一步只是「建立关系」，真正的读权限另外配（见坑 3）。

gcloud compute backend-buckets create static-site-backend \
  --gcs-bucket-name=lukecheng-static-site \
  --project=$PROJECT

2.3 建 URL map（决定请求怎么路由）

默认所有请求都打到 backend bucket；后面根路径的 301 也在这里加。

gcloud compute url-maps create static-site-urlmap \
  --default-backend-bucket=static-site-backend \
  --project=$PROJECT

2.4 建 HTTP target proxy

代理层，把 forwarding rule 收进来的流量交给 URL map。

gcloud compute target-http-proxies create static-site-http-proxy \
  --url-map=static-site-urlmap \
  --project=$PROJECT

2.5 建 80 端口 forwarding rule（真正对外）

把静态 IP 的 80 端口接到 proxy 上。到这一步 LB 才真正存在。

gcloud compute forwarding-rules create static-site-http-rule \
  --address=static-site-ip \
  --global \
  --target-http-proxy=static-site-http-proxy \
  --ports=80 \
  --project=$PROJECT

2.6 用 IP 验证链路

LB 配置下发要 1~2 分钟，别建完立刻测。

IP=$(gcloud compute addresses describe static-site-ip --global --format='value(address)')

curl -sI http://$IP/index.html
curl -sI http://$IP/img/test.jpg
结果说明去哪看
200链路通，权限也对可以直接下一步
403 Forbidden + Server: UploadServerLB 到了 GCS，但 bucket 私有拒绝匿名读坑 3
404 + Google 样式错误页LB 活着，但 bucket 里没这个对象查文件名/路径
Connection timed out包没到 LB等下发 / 换网络出口

今天踩的 4 个坑（这部分最值钱）

坑 1 · gcloud: command not found

现象：install.sh 明明跑完了，`gcloud --version` 还是找不到命令。

原因：用了 --quiet，安装脚本跳过了「把 PATH 写进 bashrc」那一步。二进制其实已经装好了，只是 shell 找不到。

验证 / 修复：

# 先证明它装好了
/root/google-cloud-sdk/bin/gcloud --version

# 永久加进 PATH（顺带补全）
echo 'source /root/google-cloud-sdk/path.bash.inc' >> ~/.bashrc
echo 'source /root/google-cloud-sdk/completion.bash.inc' >> ~/.bashrc
source ~/.bashrc
gcloud --version

教训：source ~/.bashrc 救不了「bashrc 里压根没这行」的情况。

坑 2 · curl 完全没反应

现象：curl -sI http://IP/ 敲下去，什么都不打印，也不报错。

原因：-s 是静默模式，连错误信息一起吞了。「没输出」不等于 200，也不等于 404，可能是超时。

正确姿势：调试时永远不要只加 -s，要加 -v 和超时：

curl -v -m 15 http://$IP/ 2>&1 | head -30
nc -vz -w 5 $IP 80

教训：-s 是给脚本用的，不是给排查用的。

坑 3 · 403 Forbidden（bucket 私有）

现象：

HTTP/1.1 403 Forbidden
Content-Type: application/xml
X-GUploader-UploadID: AFy3sg...
Server: UploadServer

判断：Server: UploadServer + X-GUploader-UploadID 是 GCS 的特征头——说明请求已经穿透 LB 打到了 GCS，只是 GCS 拒绝了匿名访问。链路是通的，问题只在权限。

修复（静态站公开读）：

# 先给公开读（能读对象）
gcloud storage buckets add-iam-policy-binding gs://lukecheng-static-site \
  --member=allUsers --role=roles/storage.objectViewer

# 但这个角色也能「列目录」，换成只能读文件、不能列目录的
gcloud storage buckets remove-iam-policy-binding gs://lukecheng-static-site \
  --member=allUsers --role=roles/storage.objectViewer

gcloud storage buckets add-iam-policy-binding gs://lukecheng-static-site \
  --member=allUsers --role=roles/storage.legacyObjectReader

两个角色的区别：objectViewer = 能读 + 能列目录（会泄露文件清单）；legacyObjectReader = 只能按名字读，不能列目录。

教训：403 + GCS 特征头 = 权限问题，不是 LB 配置问题。

坑 4 · 根路径 / 打不开，还一度泄露文件列表

现象一：curl -sI http://IP/ → 404 Not Found（Google 样式错误页）。

原因：Cloud Storage backend bucket 没有「默认首页」概念。LB 收到 GET / 会去 bucket 找一个名叫 /（空）的对象，找不到就 404。它不会自动把 / 翻译成 /index.html。

现象二（更糟）：给 bucket 加了 objectViewer 之后，GET / 变成 200，但返回的是这种 XML：

<ListBucketResult><Name>lukecheng-static-site</Name>...
<Key>img/test.jpg</Key>...<Key>index.html</Key>...

这是 bucket 的文件清单——因为 objectViewer 带「列目录」权限，匿名用户把你的文件全列出来了。这不是「好了」，是更严重的暴露。

正确修复：在 URL map 里加一条 301，只把 / 重定向到 /index.html（其他路径不动）。

cat > /tmp/urlmap.yaml <<'EOF'
name: static-site-urlmap
defaultService: https://www.googleapis.com/compute/v1/projects/lukechengtest/global/backendBuckets/static-site-backend
hostRules:
- hosts:
  - "*"
  pathMatcher: allpaths
pathMatchers:
- name: allpaths
  defaultService: https://www.googleapis.com/compute/v1/projects/lukechengtest/global/backendBuckets/static-site-backend
  routeRules:
  - priority: 1
    matchRules:
    - fullPathMatch: /
    urlRedirect:
      pathRedirect: /index.html
      redirectResponseCode: MOVED_PERMANENTLY_DEFAULT
EOF

# 导入前先看文件写对没
cat /tmp/urlmap.yaml

# 导入（会提示 overwrite，输 y）
gcloud compute url-maps import static-site-urlmap --global --source=/tmp/urlmap.yaml

# 关键：确认规则真的进去了（不为空才对）
gcloud compute url-maps describe static-site-urlmap --global --format='value(pathMatchers)'

为什么用 301 而不是 rewrite：urlRedirect 兼容性更好（rewrite 的 urlRewrite 在部分 gcloud 版本会被忽略，导进去也看不到）。对静态站来说，301 到 /index.html 完全够用。

验证：

curl -sI http://$IP/              # 301 + Location: /index.html
curl -sIL http://$IP/             # 跟随：301 → 200 + text/html
curl -sL  http://$IP/ | head -10  # 看到 <h1>Hello from Cloud Storage...</h1>

教训：200 不等于「对了」——要看你 200 回来的是什么内容。

明天要做：DNS / HTTPS / CDN

第三步 · Cloud DNS 子域委派

把 static.cloudworkflowdone.com 交给 GCP 解析（不是加到 Cloudflare 代理，因为要练 GCP 自己的 CDN）。

PROJECT=lukechengtest

# 1) 启用 API + 建 public zone
gcloud services enable dns.googleapis.com --project=$PROJECT

gcloud dns managed-zones create static-site-zone \
  --dns-name=static.cloudworkflowdone.com. \
  --description="Static site: GCS + HTTPS LB" \
  --visibility=public \
  --project=$PROJECT

# 2) 拿 4 个 NS 地址（Cloudflare 要用）
gcloud dns managed-zones describe static-site-zone \
  --format='value(nameServers)' --project=$PROJECT

# 3) 在 zone 里加 A 记录 → LB IP
gcloud dns record-sets create static.cloudworkflowdone.com. \
  --zone=static-site-zone --type=A --ttl=300 \
  --rrdatas=136.82.37.171 --project=$PROJECT

Cloudflare 操作：DNS → Records → Add record，Type NS，Name static，把 GCP 给的 4 个 NS 一条一个加进去，Proxy status 必须是 DNS only（灰云）。如果之前给 static 建过 A/CNAME，先删掉。

dig +short NS static.cloudworkflowdone.com      # 4 个 googledomains.com
dig +short static.cloudworkflowdone.com         # 136.82.37.171
curl -sI http://static.cloudworkflowdone.com/   # 301
NS 委派生效要等几分钟到十几分钟，dig 不到先别慌，等 5~10 分钟再试。

第四步 · Google 托管证书 + HTTPS

# 1) 建证书（会先 PROVISIONING，等 DNS 验证）
gcloud compute ssl-certificates create static-site-cert \
  --domains=static.cloudworkflowdone.com --global --project=$PROJECT

# 2) HTTPS proxy
gcloud compute target-https-proxies create static-site-https-proxy \
  --url-map=static-site-urlmap \
  --ssl-certificates=static-site-cert --project=$PROJECT

# 3) 443 forwarding rule
gcloud compute forwarding-rules create static-site-https-rule \
  --address=static-site-ip --global \
  --target-https-proxy=static-site-https-proxy \
  --ports=443 --project=$PROJECT

# 4) 查证书状态：PROVISIONING → ACTIVE 才算成功
gcloud compute ssl-certificates describe static-site-cert --global \
  --format='value(managed.status,managed.domainStatus)' --project=$PROJECT

证书 ACTIVE 后验证：

curl -sI https://static.cloudworkflowdone.com/
echo | openssl s_client -connect static.cloudworkflowdone.com:443 \
  -servername static.cloudworkflowdone.com 2>/dev/null \
  | openssl x509 -noout -issuer -subject

issuer 应该是 Google Trust Services（不是 Let's Encrypt——这次是 Google 托管证书）。

第五步 · 开 Cloud CDN 验证缓存

# 给 backend bucket 开 CDN
gcloud compute backend-buckets update static-site-backend \
  --enable-cdn --project=$PROJECT

# 第一次请求：MISS
curl -sI https://static.cloudworkflowdone.com/img/test.jpg | grep -iE 'age|cache'

# 再请求一次：应该 Age > 0（命中缓存）
curl -sI https://static.cloudworkflowdone.com/img/test.jpg | grep -iE 'age|cache'

验证点：第二次响应出现 Age: 数字，说明命中 CDN 缓存。之后再做练习要求的 3 个破坏-修复（bucket 私有 403 / 关 CDN 改 TTL / DNS 指错）。

收尾清理（防扣费）

练完不需要保留的话，按依赖顺序删（先删引用方，再删被引用方）：

# 1) 删转发规则和代理
gcloud compute forwarding-rules delete static-site-http-rule --global --quiet
gcloud compute forwarding-rules delete static-site-https-rule --global --quiet
gcloud compute target-http-proxies delete static-site-http-proxy --quiet
gcloud compute target-https-proxies delete static-site-https-proxy --quiet

# 2) 删 url map / backend bucket / 证书 / IP
gcloud compute url-maps delete static-site-urlmap --quiet
gcloud compute backend-buckets delete static-site-backend --quiet
gcloud compute ssl-certificates delete static-site-cert --global --quiet
gcloud compute addresses delete static-site-ip --global --quiet

# 3) 删 DNS zone（可选）
gcloud dns managed-zones delete static-site-zone --quiet

# 4) 删 bucket（连同内容）
gcloud storage rm -r gs://lukecheng-static-site
删之前先在 Cloudflare 把 static 的 NS 记录撤掉，避免留下悬空委派。

命令速查（今天已验证的部分）

从头到尾一次跑完的顺序（假设 bucket 和内容已经准备好）：

PROJECT=lukechengtest

# --- 建 bucket ---
gcloud storage buckets create gs://lukecheng-static-site \
  --location=us-central1 --uniform-bucket-level-access

# --- 上传 ---
cd ~/static-site
gcloud storage cp -r . gs://lukecheng-static-site/ --exclude='.DS_Store'
gcloud storage ls -r gs://lukecheng-static-site/

# --- LB 五件套 ---
gcloud compute addresses create static-site-ip --global --project=$PROJECT
gcloud compute backend-buckets create static-site-backend \
  --gcs-bucket-name=lukecheng-static-site --project=$PROJECT
gcloud compute url-maps create static-site-urlmap \
  --default-backend-bucket=static-site-backend --project=$PROJECT
gcloud compute target-http-proxies create static-site-http-proxy \
  --url-map=static-site-urlmap --project=$PROJECT
gcloud compute forwarding-rules create static-site-http-rule \
  --address=static-site-ip --global \
  --target-http-proxy=static-site-http-proxy --ports=80 --project=$PROJECT

# --- 权限（公开读，但不能列目录）---
gcloud storage buckets add-iam-policy-binding gs://lukecheng-static-site \
  --member=allUsers --role=roles/storage.legacyObjectReader

# --- 根路径 301 到 index.html（见坑 4 的 YAML）---
gcloud compute url-maps import static-site-urlmap --global --source=/tmp/urlmap.yaml

# --- 验证 ---
IP=$(gcloud compute addresses describe static-site-ip --global --format='value(address)')
curl -sI http://$IP/
curl -sIL http://$IP/
curl -sL http://$IP/ | head -10
一句话记住今天
建站不是「把文件传上去就完事」——LB 是五件套（IP / backend bucket / url map / proxy / forwarding rule），权限是单独一层，根路径要单独映射。每一层都要有自己的验证方法，出问题才能定位到具体哪一层。
